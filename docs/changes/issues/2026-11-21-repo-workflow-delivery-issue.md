## 背景与目标

将个人开发交付习惯集中到可跨仓库使用的 `workflow-delivery`。对外只有一个入口，按用户意图、当前阶段和已有授权加载内部规则。

## 范围与排除项

- 将 `workflow-change` 改名为 `workflow-delivery`，将 `workflow-tests` 并入验证流程，移除两个旧入口及 Observer Skill 和调用入口，保留历史观察日志。
- `references/` 使用 `flow-issue.md`、`flow-verification.md`、`flow-acceptance.md`、`flow-commit.md`、`flow-archive.md`、`flow-release.md`。正文维护共同约束和意图分流，日常验证与发布验证共用验证流程，仅本地提交时复用已有结果。
- `assets/` 使用 `template-issue.md`、`template-commit.md`、`template-archive.md`。归档模板默认提供公开标题、稳定工作项标识、实际完成日期和交付摘要，优先采用目标项目已有格式。发布审定清单写在发布流程中。
- 归档流程按目标项目约定准备并确认摘要。目的地、标签、字段、发布方式及官网读取约定由项目定义。更新 Codex 展示配置和仓库现行规则中的 Skill 引用。
- `flow-archive.md` 仅在项目启用归档且本地工作项已完结时准备或核对公开摘要。摘要写明实际交付，并在可公开时链接到 GitHub 上可访问的对应工作项或源码；沿用稳定工作项 ID。进行中的状态留在本地。
- 临时追加事项先对照当前 Issue 的目标、范围和验收标准。同一交付的补充或修正按现有授权处理，超出批准范围时先确认。差异较大或可独立交付、验收或回滚时，说明差异并建议单独建 Issue，待用户同意后按项目规则建档或排队。
- 开始新 Issue 前检查本地是否仍有已开工且未完结的 Issue。有则先收尾当前 Issue。排队不占活动名额，队列默认最多 5 条，满了先记入收件箱；项目有明确约定时按项目规则执行。
- 验收结论统一为「验收通过」，仅在本期范围内的验收项全部通过后记录。尚有验收项未通过时保持待验收；用户明确决定某项本期不做时，在 Issue 注明或从本期范围和验收标准中移除，再按剩余范围验收。
- 官网 Skills 介绍和源码链接更新暂缓。如后续恢复，建议单独建网站 Issue。
- GitHub Actions、API 写入与历史补录属于归档实现，需在对应工作项中确认范围。官网归档数据展示暂缓。历史 Changelog 和观察记录保留原有记载。

## 验收标准

- 用户可用不同自然表达进入建档、验证、验收、提交、归档或发布流程。意图识别和写入授权分别判断。
- Skill 可用于其他仓库。项目有约定时按项目执行，未启用归档时可以照常完结工作项。
- 用户临时追加与当前目标差异较大的要求时，Skill 说明差异并建议拆分 Issue。当前交付内的补充继续按现有范围和授权处理。
- 当前 Issue 未完结时，Skill 不启动下一条。验收项未全部通过时保持待验收，经用户明确调整本期范围后按剩余验收项判断是否通过。
- 只为已完结的工作项准备归档。重复归档沿用原工作项 ID，项目未启用远端归档时可以照常进行本地交付。
