## 背景

现有 local-issue-commit-workflow 已提供本地工作项、验收与提交管理，但追加范围、拆分提交、失败恢复和最终记录整理规则不够明确，部分内容重复或过于严格。用户希望持续积累开发协作中的观察，经过考察再判断是否值得形成真实需求和 Skill 补丁；普通聊天不参与观察。根 README 仍以历史迁移和构建说明为主，产品功能、安装入口及包结构也需更新。

## 目标

形成职责清晰、可持续维护的开发工作流与观察机制，并让根 README 准确介绍当前项目、安装开发入口和两份 Skill。

## 范围与已确认设计

### 本地变更工作流

- 将 skills/local-issue-commit-workflow 整理为 workflow-change，显示名称为“本地变更工作流”；同步入口、调用配置、模板、参考和有效引用。
- 保留本地 Issue 与 Commit 记录关联、用户验收和提交批准边界、提交同步结项、失败保持真实状态等有效规则。
- 明确任务讨论、实施、当前交付补充、独立新目标、提交拆分和跨会话恢复的处理；已明确批准的范围不重复请求同一份批准。
- 默认按交付与回滚边界组织提交；用户可明确批准多笔提交，最后一笔同步结项，部分失败时保留成功结果。
- 修正删除已有改动的错误建议、提交前用 git log 检查新消息的时序问题及模板重复状态；最终记录维护当前交付结果，不堆叠被取代的中间结论。
- 优先采用目标仓库规则，不把 Exts 的路径、语言、平台和测试限制强加给其他仓库；不自动建立未经批准的项目管理体系。
- 用户追加要求明确与 Superpowers 配合：复用已批准工作项及设计，按需调用专项方法，仓库禁止的子代理、并行、提前提交和视觉测试不因 Skill 建议而获得许可。

### 开发工作流观察

- 新增 workflow-observer，负责开发协作事实的记录与按需复盘，不负责实施业务或自行修改其他 Skill。
- 仅在项目开发任务明确使用相关 Skill 时，按该工作流执行观察；普通聊天、仅打开项目、泛泛提及代码均不触发。调用与发现方式在设计中明确，避免广泛隐式触发。
- 按目标项目保存日志，建议位置为 docs/skills/workflow-observer/observations.md；有实际观察后再记录，不批量创建空日志。
- 记录日期、开发场景、可核对事实及来源，区分用户明确表达、代理实际行为和待考察的推测。不得将一次选择固化为永久偏好，也不得将项目约定直接推广为全局习惯。
- 观察不等于真实需求；重复发生也只是证据。经过后续使用和复盘，判断应修正执行、修改项目规则、提出 Skill 补丁、继续观察或搁置，不设次数达标就升级的门槛。
- 每月一次整理提醒作为试行频率；提醒的是复盘观察，不是要求更新 Skill。没有足够开发记录可以跳过，已暂缓事项无新证据时不重复催促。
- 影响当前开发的明确错误或规则冲突及时指出；其他观察在适当开发节点记录，不要求每条观察立刻处理，也不要求每次复盘产生补丁。
- 月度提醒的具体触发及持久状态方案在设计阶段确定，并遵守仅在开发 Skill 使用场景生效的边界；本轮不创建后台定时自动化。
- 实际修改 Skill、仓库规则或个人记忆前仍需相应明确批准；观察日志不是自动改写规则的授权。

### 根 README

- 核对根命令、工具版本、平台要求、公共 dist、正式与开发配置隔离及共用下载目录，修正过时的迁移叙述和包结构；详细规则链接至现有文档。

- 用户追加批准将名称统一为 workflow-change，并在官网产品介绍的 Skills 分类中加入 workflow-change、workflow-observer 的简短用途和源码入口；复用已有模块展示，不改布局或新增组件。

## 验收标准

- 变更工作流能处理简单任务、明确文案修改、当前范围补充和多笔提交，避免重复批准、擅自删除已有改动及虚假完成状态。
- 从仓库事实可恢复正确工作位置；文档只维护最终有效结论，验收与提交批准不重复维护多份。
- Observer 仅在开发任务使用相关 Skill 的场景生效；普通聊天不触发、不记录。跨项目使用时读取目标仓库规则，观察归属于对应项目。
- 观察、推测、候选改进与实际补丁有清晰边界；能保留未确认、被推翻及暂缓的观察，不以数量或时间强制升级。
- 月度提醒可说明上次复盘与本次是否需要提醒的依据；无足够观察可跳过，真实补丁需明确批准。
- 用纯讨论、小任务、连续文案修正、追加范围、多笔提交、部分失败及跨会话恢复场景核对判断，不新增视觉或交互验收自动化。
- 根 README 与现有产品、命令、平台、包结构和两份 Skill 一致，本地链接有效；不把内部工作管理规则变成公开项目介绍。
