# 按变更影响范围执行验证

## 元信息

- 工作项：2026-11-05-repo-scoped-verification
- 状态：已完成
- 当前阶段：用户批准本地提交，代码提交完成，随文档提交完结
- 规模：小型规范任务；新增 CI 自动化、缓存或依赖分析工具需另行明确范围。
- 批准依据：用户先要求记录方案，后明确要求“加一个tets的 把刚才的加进来”；据此新增仓库内 tests Skill，并同步独立规范与根规范的冲突表述。不安装全局 Skill，不修改 CI。

## 背景

阶段结束固定执行完整测试、类型检查和构建，对纯静态资源改动成本偏高。随着 monorepo 扩大，必须区分功能、应用和全仓库的检查范围，防止本地提交重复触发验证。

## 目标与拟议范围

- 将分级验证规则维护在独立 docs/verification.md，AGENTS.md 保留简短强制入口与关键约束，并同步替换与新策略冲突的阶段完整验证表述。
- 变更分级：文档只查必要格式与链接；静态资源查有效性和引用，影响打包时构建所属应用；界面调整按影响运行类型检查与构建，用户验收视觉与交互；业务逻辑运行对应行为测试；目录迁移运行所属应用完整检查；公共包和根配置检查直接受影响项目，只有确实影响全仓库才扩大。
- 用户追加批准“同步更新官网 产品介绍/skills”：在现有 Skills 产品数据中新增 tests 介绍与源码链接，保持页面结构与其他内容；属于本 Skill 交付的介绍同步，不部署或发布。
- 区分完整功能检查、完整应用检查与完整仓库检查；不因功能或应用数量增加，就固定扩大每次验证范围。
- 验证后无相关变化则复用结果；代码、配置、依赖、生成输入或环境变化影响结果时，只重新运行失效检查。Issue/Commit 记录注明实际命令、范围、结果和未验证事项，不增加单独的结果数据库。
- 用户要求本地提交后不再跑测试、类型检查或构建，不重新调查或增加验收；复用已有结果，准确记录未执行项。
- 使用现有路径与依赖关系判断影响，不在本任务新增工具、复杂自动化或配置体系；无法确认边界时保守扩大至受影响应用，而非直接检查全仓库。
- 完整检查放在影响范围较大的开发交付，以及合并/发布的必要关口；没有可复用结果才执行相应检查。CI 按受影响项目兜底是后续配置方向，不能写成当前已具备；缺少 CI 时明确剩余验证，不伪称安全关口存在。
- 测试覆盖对应用户行为和真实风险，避免重复覆盖与实现细节断言；不借规范任务扩大测试或顺手清理现有测试。

## Skill 拆分建议

已按用户要求新增仓库内 skills/tests/SKILL.md，将“识别改动 → 判断影响 → 选择最少充分检查 → 复用结果 → 如实报告”独立为按需触发的 tests Skill。Skill 不重复项目命令和门禁，不默认启动额外测试，不在用户只要求本地提交时触发。已有 workflow-change 只增加按需衔接入口；未安装全局副本。

其他规范候选只记录建议，不纳入本任务迁移：开发/验收/提交流程、Web UI 来源与定制边界、品牌源稿与派生资源、构建分发与稳定产物、版本和依赖规则。已有独立文档优先复用；纯声明规则通常无需单独 Skill。

## 排除项

- 不改变应用功能、构建产物、依赖或权限，不增加测试框架、守卫、日志平台或性能统计体系。
- 不新增或修改 CI，不配置缓存或安装全局 Skill；这些动作需要具体方案批准。
- 不改动当前 Logo 工作项或目录迁移范围，不提交或推送。

- 从变更类型能明确选出检查范围；完整应用与全仓库验证有清楚触发条件。
- 无相关变更不重复验证，本地提交不追加验证；未执行项如实报告。
- AGENTS、独立文档和可选 Skill 不存在重复或冲突的强制检查链。
- 官网 /features/#skills 显示 tests 的用途与源码链接，沿用现有条目布局；源码链接目标需在提交并推送后才会公开更新。
