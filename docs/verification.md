# 按变更影响范围验证

本文件维护仓库验证策略。根 AGENTS 保留强制入口；[workflow-tests Skill](../.agents/skills/workflow-tests/SKILL.md) 提供检查选择方法，不复制项目命令或建立第二套规则。用户最新明确要求及特定风险的现行要求优先。

## 按改动选择检查

| 改动 | 必要检查与边界 |
| --- | --- |
| 纯文档、Skill | 本次文件的格式、相对链接与规则一致性；Skill 元数据及相关场景审阅。不运行应用测试、类型检查或构建 |
| SVG、图片等静态资源 | 文件可解析、引用与生成输入正确；影响打包时构建所属应用。不运行无关业务测试或仅因资源修改运行类型检查 |
| 样式、界面文案 | 检查引用；修改 TS/TSX 时运行所属应用类型检查，影响编译或样式产物时构建。无逻辑变化不跑业务全量测试；视觉与交互由用户验收 |
| 局部业务逻辑 | 对应行为测试与所属应用类型检查；影响打包、运行入口或依赖图时构建。阶段完成不自动追加无关模块测试 |
| 跨模块行为、公共应用基础能力或大范围目录迁移 | 阶段结束执行所属应用完整测试、类型检查与构建，不重复执行已覆盖且仍有效的针对性检查 |
| 公共包、依赖或根构建配置 | 检查直接受影响包及其消费者；依赖升级仍按版本规则执行安装、测试、构建。只有影响确实跨越整个仓库时才扩大到全仓库 |
| 更新产品版本、准备发版本 | 整理上一正式版本以来的全部变化，先展示版本与 Changelog 草稿供用户审定，确认后写入并完成下述全量发布验证；不因最终 diff 只有版本字段和日志就降为局部检查 |
| 仅本地提交 | 不重新测试、类型检查、构建或附加文档检查；复用结果并按提交流程同步终态、核对暂存边界、提交和核对结果 |

目录数量、文件数量和测试数量不作为全量验证的触发条件。沿实际引用和依赖判断；不确定时先扩大到受影响应用。明确安全、权限、数据或兼容性风险需补充对应验证，不以等待时间为由省略必要风险检查。

## 产品版本与全量发布验证

- 用户要求更新产品版本或准备发版本，即进入发布准备；先整理上一正式版本 Tag 至当前交付的提交和必要 diff，按官网日志规范展示拟用版本号、标题、分类与逐条正文草稿，等待用户审定，确认后才写入版本与 Changelog，不得直接修改后让用户返审。已有明确审定的版本和文案不重复确认。全量验证在发布准备阶段完成，不能只改数字。仅总结、询问版本建议或维护 Skill 不触发应用全量检查；只要求本地 commit 不重新进入发布准备。
- 全量覆盖仓库现有的根构建/发布脚本测试、Website 现有纯逻辑测试、Extension 全部逻辑测试、API 完整测试、内部工具包现有测试与检查、Desktop 既有可自动化的纯逻辑测试，以及官网/扩展类型检查、官网构建和双端发布打包。根据各项目脚本、README 与[构建发布规范](build-release.md)选择实际入口，不新造框架或引入视觉、焦点、菜单交互测试，不为当前未改动的应用省略现有全量范围。
- 本机按平台运行可执行部分；macOS 原生测试和双端打包必须在 macOS 完成。无隔离数据库而跳过的 API 实库测试、不可用的平台检查等明确记为待验证，不称为完整通过，不借用生产环境验证。现有 GitHub Release 检查仅按实际配置认定覆盖，未配置或未运行的检查仍是缺口。
- 开始发布准备后运行一次全量检查，不能复用日常开发的局部验证冒充全量；同次发布准备中对应当前输入的完整结果可以复用。修复后只重跑受影响且失效的部分，不无条件循环全量。
- 发布检查包含已知失败和测试/实现/现行规范冲突；不能以历史遗留或与本次版本文件无关为由放行。未经明确批准不删除、跳过失败测试或扩大修复范围。失败未解决记为发布验证不通过，缺少检查记为未完成；用户明确要求本地提交时可如实记录后提交，但不因此声称发布就绪。
- 全量检查须同时审查测试适用性及实际执行入口：清点活动测试，结合版本区间变更追踪生产调用，识别过期契约、无调用代码的测试、重复覆盖、实现细节/样式断言和入口遗漏。不得仅凭失败、mock或readFile决定删除，产物完整性和失败保留的文件断言仍有实际价值。结果列出具体文件与用例、证据及保留/更新/合并/删除/必要补充建议；测试不合适、产品回归、CI未覆盖与环境跳过分别记录。未经批准不改测试、业务或CI，不以数量多为由裁减。审查可与同次发布验证结果一并复用，后续只复核受影响部分，不反复从头通读。
- 全量验证在版本与日志交付验收前完成，不等到普通 commit 阶段追加。GitHub 发布前仍独立验证干净提交；本规范不自动授权修改 CI、提交、推送、打 Tag 或发布，浏览器视觉和真实交互继续由用户验收。

## 完整检查与结果复用

- 日常开发的完整功能检查只覆盖目标行为，完整应用检查只覆盖该应用；修改 extension 不默认检查 website、desktop 或 API。产品版本发布准备是上述全量检查的独立触发条件。
- 影响面较大的开发交付需要完整应用检查；合并时依据目标和现有门禁补齐必要检查，没有相关输入变化则复用结果。发布准备按上述专节执行，发布打包和平台构建遵循构建分发规范。
- 代码、构建配置、依赖、生成输入、有关环境改变时，重新运行受影响且已失效的检查；无关文档变化不使代码检查失效。旧结果无法确认对应范围时如实标记未验证，不视为通过。
- 直接在现有 Issue/Commit 记录保存实际命令、范围、结果及限制，不建立额外的结果数据库或强制扫描流程。
- 需要重新检查时只运行一次相应范围；失败处理、一次定位与一次重试上限、内存告警熔断和串行执行继续遵守根规范。
- 用户要求本地提交后，不启动新的验证或 Skill 链，不追加浏览器验收，不阻塞在未执行的检查上；明确记录已有结果与未验证项。

## 控制长期成本

测试对应用户行为和真实架构边界，同一行为保留一个主要验证层级，不随任务不断积累重复测试、源码文本断言和额外守卫。不因本策略顺手重写或清理无关测试。

优先使用现有功能测试、应用边界与真实依赖划分影响。按路径配置 CI、构建缓存和慢测试管理是可选的后续独立工作，本规范不代表这些能力已配置，也不自动批准新增工具或 CI 改动。

用户负责 Chrome/Edge 视觉与交互验收；代理只验证逻辑、配置、构建和必要边界。自动化通过不等于用户验收通过。
