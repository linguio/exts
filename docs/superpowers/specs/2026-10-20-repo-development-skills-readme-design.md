## 目标与职责

交付 workflow-change、workflow-observer 和准确的根 README。两个 Skill 分别管理开发交付与开发协作观察；观察积累证据，不能自动转成需求、偏好或规则。

| 位置 | 职责 |
| --- | --- |
| workflow-change | 恢复当前任务，明确授权与范围，维护工作项，组织验收和提交收尾 |
| workflow-observer | 在开发 Skill 使用场景中记录事实，按需复盘，提出有依据且可被否决的改进建议 |
| 目标仓库 AGENTS 与工作项 | 决定实际目录、语言、操作授权、验证要求及动态状态 |
| 目标项目观察日志 | 保存该项目的观察、证据、复盘结论及提醒日期，不写入 Skill 源稿或个人记忆 |
| 根 README | 面向读者介绍现有产品、安装开发入口、项目结构及两份 Skill 用途 |

## 变更工作流

- 明确的修改指令与紧邻方案的批准可以形成实施授权；讨论、询问建议不等于允许改文件。已有授权持续适用于已确认范围，不因切换 Skill 重复申请。
- 开始或恢复时只检查当前决策所需的仓库规则、活动工作项、分支、工作区和相关提交；保留已有改动，不擅自认领或删除其他工作的内容。
- 区分当前交付的补充、验收修正和独立目标。用户明确批准合并的范围同步到当前工作项；独立新工作遵循仓库队列规则，无法判断时才询问。
- 默认一个完整交付；按用户要求准备多笔提交的文件边界和完整消息。“拆分 Commit”只准备方案，“提交到本地”只执行已展示且获准的本地范围，不能据此推送或发布。
- 提交前核对暂存内容与待用消息，提交后核对实际消息和工作区。多笔部分失败时保留成功结果，只恢复未完成部分的真实状态，遵守仓库终态规则，不自动回滚、重做或扩大批准。
- Issue 维护当前批准范围、剩余事项和下一步；交付记录在收尾时整理成最终结果、有效验证、未验证限制、用户验收及批准，不保留已被取代的中间结论。
- 精简入口，条件性细节放现有参考文件；模板各自只维护一处验收和提交批准状态。默认目录及中文消息约定可被目标仓库规则替代。

## 与 Superpowers 配合

- workflow-change 负责工作项与授权事实，Superpowers 按实际任务提供 brainstorming、writing-plans、executing-plans、systematic-debugging、writing-skills 和 verification-before-completion 等方法；不在每个任务中机械调用整套技能。
- 共用已批准的 Issue、设计和必要 Plan；不因技能切换重复建档或请求同一范围的批准。项目明确禁止的子代理、并行执行、提前提交或视觉测试不会因技能建议而获得许可。
- 无 Superpowers 时，两个 Skill 仍可独立使用；缺少专项方法只在影响当前交付时说明。Observer 收集的事实仍受开发场景及日志授权边界限制。

## Observer 的调用与记录边界

- Observer 配置 allow_implicit_invocation: false；普通聊天、仅打开项目或提及代码都不进入观察流程。
- 初版由正在使用的 workflow-change 在阶段收尾时明确读取并执行相邻 Observer 的相关指引，或由用户在项目开发任务中明确调用；不在其他 Skill 中批量添加入口。
- Skill 文件可用不代表日志写入已获授权。首次接入项目时明确日志位置和允许记录的范围；沿用已确认授权，仍服从项目对工作项范围及文件变更的要求。未获写入授权时只在本次报告中说明候选事实，不自行持久化。
- 只处理参与当前开发任务时已经获得的信息，不读取其他聊天、应用或私人活动；不为收集观察额外监控用户或启动后台进程。
- 对同一任务内持续修正文案等情况，保留与判断有关的上下文，避免把每次修改都拆成独立日志。
- 只在有可核对事实或具有明确上下文的待考察线索时记录；不为每次任务生成固定篇幅的观察，也不要求必须发现问题。
- 无法读取配套 Observer 时继续完成开发任务，在相关报告中如实说明观察能力不可用，不自动安装。

## 日志与复盘

每个项目按需建立 docs/skills/workflow-observer/observations.md。仓库已有合适位置时沿用，不预建所有 Skill 的空日志。

文件顶部保存首次记录日期、上次实际复盘日期、上次月度提醒月份及可选的暂缓说明。日志条目包含日期、涉及任务或 Skill、开发场景、原始事实及依据；推测与事实分开，后续补充支持或反对证据及复盘结论。

- 用户明确要求、代理执行失误、项目特例和待考察的习惯线索分开判断。一次选择不是永久偏好，出现多次也不自动构成需求。
- 新证据可补充到相关条目，保留观察的原始含义；已否定或暂缓的条目留下简短结论，避免同一问题被反复提出。
- 复盘允许得出继续观察、搁置、只修正执行、调整项目规则或准备 Skill 更新提案等结论，不强制流转成补丁。
- 提案应说明问题证据、适用范围、预期收益、反例与副作用，以及为何修改 Skill 比修正单次执行更合适。用户批准后才进入实际修改，并遵循目标仓库工作项流程。
- 不维护另一套当前 Issue 或提交状态，不复制完整聊天或包含凭据、个人数据的无关输出。

## 月度提醒

采用开发任务内的月度检查，不创建定时自动化。它只在上述开发 Skill 调用的阶段收尾节点运行。

1. 首次记录所在自然月用于积累，不立即发出月度提醒；日期按用户时区。
2. 进入后续自然月时，若有值得考察且尚未实际复盘的新增事实、当月未提醒，简短提醒用户是否整理日志；不能因月份到了就要求升级 Skill。
3. 发出提醒与完成复盘分别更新日期。用户未答复不视为已复盘；当月不重复提醒，没有新增有效证据的后续月份也不反复催促。
4. 暂缓事项尊重用户约定的时间或条件，没有新证据时保持暂缓。无足够观察、没有开发活动时跳过；长期未使用后只检查当前情况，不补发历月提醒。
5. 若要主动复盘，可在开发任务中直接调用，不必等到新月份。明确影响当前任务的错误或规则冲突应及时处理，不受月度提醒限制。

## 根 README 提纲

1. 项目介绍：Exts 名称、现有标语和个人工具集合定位，删除迁移过程中的重复叙述。
2. 模块介绍：只描述 Extension、Desktop、Website、Packages、Skills 的定位与职责，不列具体功能或行为；链接各模块文档查阅细节。
3. 快速开始：官网与现有 ZIP/DMG 下载入口，扩展解压加载、DMG 拖入应用程序及首次允许打开；说明 macOS 支持范围，不承诺未经核实的在线下载结果。
4. 本地开发：按配置核对工具版本、安装命令、各端开发构建入口；说明根 build/release 的 macOS 限制，详细版本和产物规则链接至构建文档。
5. 目录与文档：按用户验收反馈，目录树只展示 .github、apps、packages、skills、docs、scripts、assets、dist，严格保持该顺序；只展开 apps 下 extension、desktop、website，不展开 packages／skills，不展示 archive。其余保留应用文档、品牌与许可证链接。
