# 观察记录与复盘

写入前确认当前调用属于开发任务、目标项目位置及允许写入的范围。当前阶段不需要记录时可跳过；不要为了运行了 Skill 就制造观察。

## 项目日志的最小结构

默认保存为 docs/skills/workflow-observer/observations.md。顶部只维护提醒与复盘所需的状态，不创建额外数据库：

- 首次记录日期：按用户时区写实际日期。
- 上次实际复盘日期：未进行，或实际完成的日期。
- 上次月度提醒月份：未提醒，或 YYYY-MM。
- 暂缓说明：按需记录用户约定的时间、事项或重新提出的条件，没有则省略。

每条观察包含日期、任务或 Skill、场景、原始事实及依据；可选推测必须单列并标为待考察。后续补充证据和复盘结论，保留原始含义，不伪造逐字引用或不可访问的会话来源。

示例结构，仅作写法参考：

```text
日期：实际观察日期
场景：任务中发生了什么
事实与依据：用户明确表达、代理实际动作及可核对文档
待考察：可能原因或潜在模式；证据不足时不写结论
后续证据／复盘：尚未考察；有新材料再补充
```

只保存理解开发过程所需的材料，不复制整段聊天、工具输出、凭据或无关私人信息。内容优先链接对应工作项、交付记录等可核对依据；跨项目不自动合并为全局档案。

## 什么值得记录

- 用户明确纠正了范围、交付形式、审批或工作方式。
- 同一问题在实际任务中再次出现，可为现有观察增加证据或反例。
- 规则与工具、仓库事实存在可核对的不一致。
- 代理发现具有具体场景依据的摩擦或改进线索，明确标注尚未确认。

普通操作、孤立口头表达和每次文案改动无需逐条归档。同一问题优先补充现有相关条目，不用条目数量制造重要性。

## 月度检查顺序

1. 确认本次处于开发 Skill 的阶段收尾，允许读取项目日志；普通聊天不运行检查。
2. 没有日志或没有实际观察则跳过。有观察但无写入权限时仅报告相关限制，不自行修改提醒状态。
3. 首次记录所在自然月先积累；后续月份核对用户时区、上次实际复盘日期、上次提醒月份及各条目的后续证据。
4. 当月已提醒则不重复。实际复盘后尚无新证据、上次提醒后无有意义的新事实、尚无足够可讨论材料，均跳过；月度到期本身不是值得复盘的证据。
5. 暂缓事项遵循用户条件。有新的相关证据时先判断是否满足重新提出条件，不因“又出现一次”自动打破暂缓。
6. 确有材料时简短邀请：“积累了一些开发观察，是否找时间复盘？当前只是观察，不代表需要更新 Skill。”邀请后记录当前提醒月份；不要据此改写实际复盘日期。
7. 用户明确要求复盘时按下文执行；用户沉默或拒绝均不标为已复盘。长期未使用后只判断当前材料，不补发过去月份的提醒。

这些是任务内判断指引，不会自行定时执行。若用户需要日历提醒或自动化，另行明确授权、范围与时间；不能让它扩大成普通聊天采集。

## 复盘方法

读取相关未处理观察，结合现有 Skill、项目规则与用户最新要求核对上下文；不要默认读完所有历史。

逐项判断：

- 事实是否可信、是否仍然有效，有没有反例或其他解释？
- 是用户稳定需求、项目约定、临时选择，还是代理没有遵循现有规则？
- 修改 Skill 能否解决问题，会不会给其他场景增加负担？
- 当前是否有足够依据提出方案，还是应继续观察、否定或搁置？

只有真正完成了这些核对并报告结论，才更新实际复盘日期。日常追加事实、月度邀请或形式上浏览文件不算一次复盘。

## 形成提案与处理结论

提案写出相关事实及反例、具体问题、适用范围、拟改规则、预期收益和副作用。没有足够证据时明确保持观察，不为每次复盘制造补丁。

用户批准实际修改后，遵循项目的 Issue、实施、验证和提交规则。观察日志可以关联最终处理结果，但不得据此自动改 Skill、用户记忆或其他项目规则。

已否定或暂缓事项保留简短原因；有新证据可重新考察。补丁是否有效需要后续真实使用验证，不能仅因文本改完就宣称已经改进用户习惯或代理表现。
