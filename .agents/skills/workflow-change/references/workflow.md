# 变更工作流参考

只在建档、恢复任务、判断范围、准备验收或提交时读取相关部分。用户最新明确批准与目标仓库规则优先；以下默认约定不覆盖项目现有体系。

## 事实与文档

Issue 是当前任务目标与范围的依据，工作台记录活动项和队列，交付记录保存最终交付与验收、提交批准。设计解释必要取舍，计划说明实施顺序；按需创建，不重复抄写整份 Issue。

默认工作项前缀为 YYYY-MM-DD-project-topic，Issue 与交付记录同时创建并互相链接。字段与路径采用项目约定；不写死当前活动任务、开发环境、版本、测试命令或个人偏好。

没有明确仓库状态约定时，采用：规划中 → 实施中 → 待验收 → 待提交 → 已完成。实际所需的批准、暂停或取消状态按项目补充，不要求每次任务机械走完每个状态。

## 用户表达与动作

| 表达或场景 | 处理 |
| --- | --- |
| 想法、建议、为什么 | 调查或提出方案，不直接改文件 |
| 对明确方案说“可以”“开始” | 执行已展示且获准的范围，不再次请求同一批准 |
| 指定一句文案如何修改 | 在当前批准范围内直接修改并同步必要记录 |
| 当前目标补充或验收修正 | 将明确获准内容同步到 Issue，继续当前工作 |
| 可以独立交付的新目标 | 遵守项目排队和单活动项约定；用户明确批准合并时记录依据 |
| 无法判断是否追加或新目标 | 先推进不受影响的工作，只澄清影响范围的缺失信息 |
| 拆分 Commit | 展示具体文件边界和消息，不自动提交 |
| 明确要求提交到本地 | 即批准当前 Issue 完结；不核实用户是否验证，不再追加验证或索要验收确认，同步 Issue、Commit 记录和工作台为已完成并本地提交，不推送 |

## 恢复任务

核对活动 Issue、当前分支、工作区、相关提交及唯一下一步。文档与代码不一致时先定位实际已完成部分，再修正记录或澄清缺口，不把旧记录直接当作最新结果。

已有改动未经归属检查不得删除、覆盖、暂存或提交。没有 Issue 的工作不等于无授权；检查用户指令和仓库规则后补齐所需记录，不擅自清理现场。

## 最终交付与验证

最终报告包含实际变更、相关检查与结果、未验证限制，以及用户可复现的验收操作和预期结果。明确区分静态检查、场景走查、自动化行为测试、用户确认与实际外部验证。

只运行与本次变更相关且项目要求的验证。没有相关变化时不重复全量检查；失败先判断业务问题、环境限制或非当前范围问题，并遵循项目重试上限。

交付记录写最终结果，不堆叠每轮聊天。替换“产物未包含”与“产物已包含”等相互过时的结论；保留必要的失败原因、替代验证和未解决限制。模板中的占位内容使用时替换或删除，不能预填验收通过。

## 提交边界与失败恢复

按用户可观察的结果、验收与回滚边界拆分，默认不因文件数量或使用了多个技能就增加提交。用户批准多笔时，一份交付记录可列出每笔范围与完整消息；最后一笔完成终态同步，记录只对整个交付负责。

按目标仓库格式生成消息。没有约定时可采用 Conventional Commits，标题说明具体结果、正文说明实际变化；不固定所有仓库必须用某种语言。提交前检查暂存 diff 及消息文本，提交后用 git log 检查实际消息，随后检查工作区。

多笔部分失败时：确认哪些提交已成功 → 保留成功部分 → 将剩余工作恢复为真实未完成状态 → 说明失败原因和后续动作。已成功提交不自动撤销或重做；原批准是否继续覆盖重试由仓库规则及是否改变文件或消息决定，不扩大批准。

一个提交前改为完成状态但提交失败时，恢复相关记录，不留下虚假完成；用户确实给过的批准事实与提交执行结果需要分别说明。

## 专项技能衔接

设计问题可用 brainstorming，复杂且有真实依赖的实施可用 writing-plans / executing-plans，故障可用 systematic-debugging，Skill 编写可用 writing-skills / skill-creator，完成前可用 verification-before-completion。选择实际需要的方法，不默认跑完整技能链。

项目限制与用户选择优先，例如禁止子代理时串行执行，禁止提前提交时只准备方案，视觉验收由用户执行时不运行浏览器替代验收。复用项目已有工作项和设计文件；不把专项技能的建议解释成用户给了新的授权。
