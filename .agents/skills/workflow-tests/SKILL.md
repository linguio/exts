# 按影响范围验证

日常开发选择最少但充分的检查，产品版本或发布准备执行全量验证。Skill 不授予修改代码、安装依赖、调整 CI 或超出用户目标修改的权限。

## 先判断任务意图

- 日常开发：按实际影响选择最小充分验证，复用仍有效的结果。
- 仅本地 commit：不启动验证，不因文件中出现版本号就自动当成一次新发布准备。
- 用户要求更新产品版本、升版本或准备发版本：进入发布准备与全量验证分支；同时按 [workflow-change](../workflow-change/SKILL.md#产品版本与发布准备) 整理上一正式版本以来的更新，先展示版本和 Changelog 草稿供用户审定，确认后才写入。测试职责不构成直接修改版本或日志的授权，也不能只看版本和日志两处 diff，套用局部检查。
- 只问版本建议、只要求总结日志或修改验证 Skill：不据此修改版本或启动应用全量测试。

## 发布准备的全量验证

- 读取仓库验证与发布规范，确认现有完整测试、类型检查、构建/打包入口及平台要求。全量范围以仓库规范为准，不能自行缩成“本次改动的几个模块”；具体命令集中维护在仓库规范，不在 Skill 另建重复清单。
- 全量验证同时审查测试是否仍然合适，不只汇总绿灯数量：清点活动仓库测试与实际执行入口，结合上个版本以来的变化，核对过期契约、已无业务调用的被测代码、重复覆盖、源码/class/像素等实现细节断言，以及应覆盖却未被执行的测试。查看相关生产调用与断言后再判断；文件读取若验证的是产物完整性、失败保留或安全边界，不得仅因 readFile 或 mock 就认定测试无效。同次发布可复用审查，输入变化后只核对失效范围，不机械逐行重读全仓库。
- 输出保留、更新、合并、删除和必要补充的具体文件/用例、证据与原因；用例不合适、产品回归、执行入口遗漏、环境跳过分开报告。失败不自动代表旧测试错，通过也不代表覆盖有效；未经批准不实施测试清理、修改业务或CI。维护只读审查结论不代替实际全量运行，也不得为追求测试数量或全绿扩大重写。
- 本次发布准备运行一次完整检查；开发阶段的局部结果不能代替，既有完整结果只有明确属于同一次发布准备且对应当前输入时才复用。后续修复后只重跑失效范围，串行、失败重试上限和资源熔断规则不变。
- 汇总已知失败与跳过项；过期测试、规范冲突也必须明确处理，不因“不是本次改的”就算通过。不得删除或跳过失败测试来放行；超出修复授权时停在具体阻塞，等待用户决定。
- 无法本机执行的检查记录为待验证，明确需要的平台或现有 CI 位置。未执行或跳过不等于通过，CI 尚未运行或没有对应 job 不等于已兜底；不得擅自新增 CI、环境或测试框架。
- 全量通过是发布准备的验收依据；后续仅要求本地提交仍不补跑。已知失败或平台待验证不阻止用户明确批准的本地提交，但必须保留“发布验证未通过/未完成”的真实结论。

## 选择与执行

- 先读取目标仓库适用规则、当前工作项的验收要求和已有验证结果；本仓库的具体策略以 [验证规范](../../../docs/verification.md) 为准。其他仓库不套用本项目路径、命令或门禁。
- 日常开发根据本次实际 diff 判断属于文档、静态资源、界面、业务逻辑、目录迁移还是公共能力变更。沿直接引用和真实依赖确认受影响功能与应用，不扫描无关项目，不以文件多或仓库变大为由升级为全仓库检查；发布准备使用上述全量分支。
- 执行前用一句话说明检查范围与原因。只为当前风险选择检查；已有稳定行为覆盖时不补重复低层测试，不新增实现细节断言或无关守卫。
- 优先复用已有结果：核对其范围、结果及验证后影响输入是否变化；只有相关输入变化或已有失败未解决才重跑受影响检查。时间流逝、补充交付记录和准备提交本身不使结果失效。不为复用检查另建缓存数据库或运行全量命令。
- 实现中运行必要的针对性检查；阶段完成时执行仓库规定的相应级别验证。完整应用不等于完整仓库；边界不清时先限定到受影响应用。
- 遵循目标仓库的串行、超时、资源、失败重试和用户浏览器验收规则。区分业务失败、环境问题与范围外问题，不为工具问题改正常业务代码。
- 报告实际执行或复用的结果、未验证项及用户验收步骤。已有 CI 和发布关口才可称为兜底；建议、未配置或未运行的检查不能记成通过。

## 停止与提交边界

- 用户只要求本地提交时不启动本 Skill，不追加测试、类型检查、构建、格式/链接扫描或场景审阅；交由提交流程复用结果并如实记录限制。
- 用户明确要求不再验证时遵从，不用 Skill 补跑检查；发现明确阻塞只报告事实，不自动扩大任务。
- Skill 自身修改只进行元数据、引用及必要场景审阅，不因此运行应用测试或构建。结构校验通过不等于行为评估或用户验收通过。
