# 本地提交

- 用户只表示验收通过时，按项目规则进入待提交。用户明确要求“提交到本地”即表示当前 Issue 可以完结并批准提交，不以用户是否实际验证、提供验证细节或看过交付材料为前提。不追问验证、不重复请求验收、不追加验证；在本地提交中在最后一笔文档提交中将 Issue 置为 `completed` 并归档。未执行的检查只如实记录，不阻止完结；提交失败时恢复待提交状态。
- 对用户明确要求免建档的改动，用户要求本地提交时只暂存并提交代码范围（实现、测试、配置和静态资源）；不得补建、更新或提交 Issue、收件箱或其他流程文档，也不得拆出文档提交。已有无关文档改动保持未暂存。
- “拆分 Commit”表示准备文件边界和完整消息，不自动表示允许提交。默认一个完整交付；多笔提交须明确边界，最后一笔同步工作项终态。
- 提交前展示或已经展示文件、diff 摘要、验证与限制、每笔完整消息及机械性终态更新。批准后只执行该范围；未经批准的其他变化不能混入原提交。
- 收到用户明确的本地提交指令后，只执行提交所必需的操作：更新当前 Issue 的交付记录和完成状态、归档路径及受影响的链接，暂存当前批准范围，执行 git commit，简短汇报结果。不要运行测试、类型检查、构建或额外的文档、链接、编码等验证，不重新调查、扩展任务或启动其他 Skill 流程，不重复索要验收和提交确认；不以缺少验证结果为由阻止提交。仅在 Git 提交失败或出现无法确定归属的改动时处理实际阻塞，不顺带做其他事。
- 用户明确要求不再验证时遵从，记录沿用结果及未验证事项，不以 Skill 流程为由补跑测试、模拟场景或子代理，也不把未执行的检查写成通过。
- 拆分已有提交前先核对本地与远端状态，说明每笔文件边界、完整消息及同步影响。原提交已在远端时，明确本地重写会造成历史分叉、普通推送无法同步；本地拆分批准不包含远端覆盖，后者须单独取得明确批准，并使用带已知远端提交限制的 force-with-lease，远端变化时停止覆盖。
- 提交前核对暂存内容和待用消息；正文采用真实 LF，可使用 -F 文件或实际换行参数。提交后核对实际消息、相关记录和 git status；不自动推送、发布、amend 或重写历史。
- 提交失败时保留成功结果，恢复未完成部分的真实状态，按仓库要求处理批准字段；不自动回滚已完成提交或重新提交成功部分。

- 先提交实现，再在最后一笔文档提交中把 Issue 置为 `completed`，并按 `date` 的年份移入 `history/<年份>/`。纯文档任务在唯一一笔提交中归档。文件名保持不变，更新受影响的链接。文档提交失败时恢复 `awaiting_commit` 和原路径，保留已成功的实现提交。
