# 建档与推进

- 讨论、问答和只读调查不创建工作项；明确修改指令或对紧邻具体方案的批准才允许相应修改。
- 用户明确要求“不要写 Issue”“免建档”或“直接改”时，跳过 Issue、Commit 记录、工作台及其他流程文档；该例外只覆盖当次明确范围，不延伸到后续改动。
- 读取适用 AGENTS、工作台和当前 Issue；检查当前仓库、分支、已有改动及相关提交，只读取本次决策需要的信息。
- 保留用户或其他工作留下的修改。发现未建档改动时先辨明归属和授权，不删除、覆盖、自动暂存或认领。
- 仓库缺少所需规则或工作台时说明缺口；未经批准不搭建新体系。用户批准的操作仍须遵守工具与环境的权限要求。

## 建档与持续推进

- 目标仓库的工作项规则决定目录、字段、阶段及提交格式。没有专门约定时，采用一份 Issue 与一份交付记录，互相链接；默认目录为 docs/ohmy-delivery/issues 与 docs/ohmy-delivery/commits，前缀为 YYYY-MM-DD-project-topic。
- 除用户明确要求免建档的改动外，新工作获批后先建档再实施；模板见 [Issue](../assets/template-issue.md) 和 [交付记录](../assets/template-commit.md)。小型任务使用足够说明实施与验收的少量 Todo，不因文件多而强制增加 Spec、Plan 或子任务。
- 当前目标的补充或验收修正，按用户明确批准更新范围后继续；独立新目标遵守仓库队列规则。已有批准持续适用于已确认范围，只有缺失信息或范围实质不明时才询问，不因技能切换重复批准。
- 建档完成后、修改代码或配置前，先展示 Issue 链接、已批准范围和唯一下一步。仅建档不等于已展示；已有实施批准时展示后继续，不重复请求确认。
- 收到状态问题时先简短回答，再继续已批准工作；收到明确暂停、取消或替换目标时遵循用户最新指令。
- Issue 只维护当前有效范围、未完成事项及下一步；交付记录收尾时整理成最终结果、有效验证和限制，替换过时结论，保留真正影响判断的失败证据。

## 队列与范围

- 启动前核对是否有已开工且未完结的 Issue，有则先收尾。排队不占活动名额，无项目约定时默认最多五条，超出先记入收件箱。
- 临时追加请求先对照目标、范围和验收标准。当前交付内的补充按已有授权推进。超范围先确认；差异大或可独立交付、验收或回滚的事项说明差异并建议拆分，待用户同意后建档或排队。
- 用户取消时保留历史记录，标记取消及未完成事项，按项目约定更新工作台。
